# PIPER CRAFT maintenance

- Read `docs/memory/README.md`, `current.md`, `problems.md` and `task_maps.md` before working. A new checkout initializes local memory using `python -m astra_vla.operation_memory compact`; machine history and graphs are untracked. For every new or resumed task run `python -m astra_vla.operation_memory planning-context --instruction "the complete current instruction"`, examine relevant maps and full real human demonstrations, and follow every `next_demo_offset`. User selection is never required.
- Before each physical task, establish the object's function, opening/closed end, operation direction, support and release conditions using common sense; a shuttlecock enters its tube cork first. Plan the next 1–3 local actions with goals, prerequisites, arm, coordinate mode, axis/sign, grasp depth, clearance/support, views, completion and stop/retreat criteria. Update from new observations after each group; do not blindly try keys or copy demonstrations. See `docs/operation_workflow.md`.
- Observe objects using `python -m astra_vla.observe --output /tmp/piper_observation` and inspect all three source PNGs and `observation.json`. Preserve source resolution, lossless pixels, timestamps and sequence numbers; screenshots only supplement UI checks. Cropping/zooming adds no information, and a gray projection does not establish an opening or closed end.
- Maintain only three-view RGB desktop control, local IK / ordinary MOVE_J, joint jog and whole-window recording. Controller-native MOVE_P and the old native_pose_probe are disabled in both UI and RPC before preparation or SDK writes.
- Before real motion, observe fresh RGB and both arms' feedback. Startup is observation only. Retain stop, input timeout, controller health, finite entry data, feedback freshness, preparation-change/configuration checks, acceleration and following budgets. Local entry, path and gripper-envelope self-collision checks are removed; telemetry/traces report collision_scope=none. Do not imply equivalent controller collision protection.
- Ordinary control, entry and recovery never reject or clip finite joint angles against URDF absolute limits/margins, including J5/J6. Validate CAN integer encoding; physical angle/speed boundaries belong to the controller. Speed settings must be positive and finite; SDK percentages remain integers 1–100. Do not infer support or reset/disable permission from history.
- F6/the coordinate button switches base and motion coordinates for both translation and rotation. Base defaults: W/S ±X, A/D ±Y, Space/Shift ±Z; I/K ∓Y rotation, J/L ±Z, O/P ∓X. Motion coordinates follow fresh SDK orientation; Piper forward/left/up are tool +Z/+Y/−X. Switching clears input, cancels automatic actions and confirms stop before changing modes; failure retains the old mode and never automatically enters control.
- SDK end-effector feedback is authoritative. Local FK is for IK and robot geometry; do not compare it to, or replace, SDK pose feedback.
- J1–J6 mouse buttons are hold-to-jog in a local control session, sending ordinary single-axis MOVE_J without TCP IK/detours or local collision checks. Keep acceleration/following guards. Release, pointer exit, focus loss, menus, arm/profile changes and stop clear input. Never enter control automatically or treat offline UI checks as hardware acceptance.
- Automatic detours continue after key release with default SDK speed 100% and 6° following budget, retaining acceleration/following guards. Esc/F9, changed input, profile/arm/mode changes, focus loss, stop and stale data cancel them. No local path or gripper-sweep collision checks apply.
- UI layout checks cover panel backgrounds, button rectangles, titles/help text and actual click targets at the minimum 1100×700 size, with profile hints, both coordinate modes and F3. Joint-panel backgrounds must not cover translation/rotation controls.
- After each held key combination ends, show actual SDK J1–J6 and gripper width/effort/enabled state. Distinguish release readback from confirmed stationary readback, label stale/missing data, and keep the latest 32 steps in telemetry/traces. Display never sends motion or proves physical success.
- Explicit scene acknowledgement may end teaching on mode=2 arms using bounded MotionCtrl_1(0,0,2), with fresh RGB, fault-free stationary feedback, mode verification and stop cancellation before/after. Address teaching arms only; never send reset, enable/disable, replay or motion targets. Failure retains pause/stop and blocks control. Offline tests are not hardware teaching-exit acceptance.
- Keep selective_wrist_prepare off; the right-arm selective wrist experiment failed and any separate retry needs continuous shoulder/elbow support. Ordinary full-arm MOVE_J recovery retains the verified near-Sleep J2/J3 recipe, speed, feedback and stop guards, but no local angle/collision checks, correction/travel/deviation budgets or enable-stage 0.75° path-deviation threshold. Limited historical recovery success does not validate every start or cold boot; see `docs/teleop.md`.
- Observe top and both wrists, including the unselected arm. For each stage assess what each view actually reveals and occludes; unclear contacts, heights or stream landing require more observation. Moving an observation arm is real motion subject to ordinary scene/feedback checks.
- Independently assess observation_views and grasp_depth before grasping, after a short lift/move, before pouring/inserting and before release. Check entry between both fingers, contact on both sides, grasp height and fingertip clearance; avoid shallow fingertip contact without blindly pushing deeper. Width, effort or a successful lift does not prove depth. Do not invent millimeter calibration or historical depth measurements.
- Support human object and human teleoperation demonstrations with three RGB views and feedback; completed recordings automatically enter Memory. Codex reviews relevant full recordings, adds titles/descriptions/tags/results/limits and keeps stable directory IDs. The legacy selector is only a focus marker. Demonstrations never authorize trajectory/key replay or replace current RGB/feedback.
- Distill only reviewed real successes into self-contained case facts, reflections, strategies and applicability limits. Nodes/transitions reference durable Memory case summaries rather than runs evidence; necessary SDK reference values include limits and are not executable waypoints. Unknown/failed/simulated cases never become successful routes. Correct/remove revoked, obsolete or failure-causing references promptly.
- Before reuse assess instruction, objects, scene, arm roles, start, backend, observation views, grasp/depth, completion and reference limits; adapt dynamically from fresh views/feedback. Promote a new strategy only after new physical success. Clearing run files does not invalidate durable knowledge; see `docs/task_memory.md`.
- Bind public Codex messages using `python -m astra_vla.public_session` for a new session. Only public text may be displayed; omit reasoning, tool output and credentials. Text itself never executes motion.
- Begin each new physical task using `python -m astra_vla.task_archive begin --name "task" --instruction "complete instruction"`. Reuse the binding across arms, stops and window restarts; `status` checks ownership. Segments and whole-window recordings share runs/task_*/; Memory merges per task. Archiving never sends robot commands. Success needs current physical/user review; unknown stays unknown. Demonstrations keep their original directory IDs; do not automatically move legacy records.
- Finish failed/aborted tasks only after necessary review and knowledge extraction using --reviewed --summary. Keep concise self-contained facts, lessons, improvements and validation limits in Memory, then delete videos, images, trajectories, key/feedback logs and result files without backups. Remove failed-operation streams and invalid evidence paths. Preserve successful cases and user-retained demonstrations; never relabel an unknown outcome merely to clean it.
- Update problems in place, separating observation, inference, change, validation and evidence. Static reads, simulations and offline tests never count as physical success; control-record finalization updates Memory automatically.
- After maintenance run `python -m astra_vla.operation_memory compact` and `python scripts/check_robot_memory.py`. Each memory page is at most 100 lines, total at most 260, with at most 12 operation summaries and 8 problems. Replace stale state and compress duplicates.
- Keep runtime records in ignored runs/ and retain only what current tasks need after extracting durable knowledge. Publish maintenance logic, docs and tests with placeholder device configuration; never commit credentials, private operation memory/graphs, raw camera recordings, control logs or sessions. Preserve the repository's license, notices and previously published demo assets.
